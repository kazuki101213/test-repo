# 02 データモデル

すべて `app` スキーマに置き、PostgREST に公開しています（`supabase/config.toml`）。

## テーブル

```
staff ──────┬──< items >──┬── products
            │             ├── payment_cards
profiles ───┘             ├──< item_photos
(auth.users との紐付け)     ├──< item_comments
                          └── lots (通番号)
expenses

```

### app.items — 中心のテーブル

仕入れた**個体 1 点**が 1 行です。これが在庫でもあり、古物台帳の買受行でもあります。

| 区分 | 主な列 |
|---|---|
| 連携キー | `sku`（一意・不変）、`lot_seq`、`is_accessory` |
| 担当 | `purchaser_id`、`deliverer_id`、`work_stream` |
| 仕入 | `purchased_at`、`cost_amount`、`marketplace`、`marketplace_item_id`、`marketplace_url`、`card_id`、`tracking_no` |
| 商品 | `product_id`、`asin`、`condition`、`accessories`、`description` |
| 販売計画 | `planned_price`、`planned_payout`、`sales_channel` |
| 作業進捗 | `arrived_on`、`product_registered_at`、`inspected_at`、`photo_uploaded_at`、`packed_on`、`shipped_on` |
| 販売実績 | `listed_on`、`sold_on`、`sold_price`、`payout_amount`、`shipping_cost`、`profit`(生成列) |
| 古物台帳 | `seller_name`、`seller_address`、`seller_occupation`、`seller_age`、`identity_check` |

`profit` は生成列なので、金額を入れれば粗利は常に正しく保たれます。

```sql
profit = coalesce(payout_amount, 0) - cost_amount - shipping_cost - other_cost
```

### status は自動で動く

作業日付が入るたびにトリガーが `status` を更新します。担当者が状態を選ぶ必要はありません。

```
仕入済 ─(arrived_on)→ 入荷済 ─(作業チェック)→ 作業中 ─(shipped_on)→ 出荷済
                                                          ─(listed_on)→ 出品中
                                                          ─(sold_on)→ 販売済
                                                          ─(returned_on)→ 返品
```

`保留` `廃棄` は手で設定したものを尊重します。

## SKU の採番

`app.build_sku()` が組み立て、INSERT トリガーが自動で入れます。

```sql
select app.build_sku(2340, 'EE', 'MM', date '2026-09-16', 12961);
-- => 2340-EEMM-20260916-1296
```

仕入金額は **10 円単位に切り捨て**ます（スプレッドシート時代と同じ）。
`packages/shared/src/sku.ts` の `buildSku()` が同じ規則で、
大元アプリは保存前に SKU をプレビューできます。

SKU を渡して INSERT した場合は、その SKU をそのまま使います（移行用）。

## ビュー

| ビュー | 用途 |
|---|---|
| `v_items` | 在庫一覧。商品マスタ・担当者・カードを結合済み |
| `v_delivery_tasks` | 納品アプリの作業一覧（未完了のみ） |
| `v_antique_ledger` | 古物台帳（買受 + 売却） |
| `v_monthly_summary` | 月次の仕入・販売・経費・純利益 |
| `v_stock_summary` | 現在庫の点数・評価額・滞留 |
| `v_deliverer_workload` | 担当者別の未完了件数・平均作業日数 |
| `v_product_performance` | ASIN ごとの仕入・販売実績と回転日数 |
| `v_amazon_listing_feed` | Amazon 在庫ファイル形式の出品データ |

すべて `security_invoker = on` なので、ビュー越しでも RLS が効きます。

## 権限

| ロール | items | products | expenses / cards | 古物台帳 |
|---|---|---|---|---|
| `admin` | 全件 読み書き | 読み書き | 読み書き | 閲覧・出力 |
| `purchaser` | 全件 読み書き | 読み書き | × | 閲覧・出力 |
| `deliverer` | **自分の担当分のみ閲覧**。更新は RPC のみ | 閲覧 | × | × |

### 納品担当者の更新を RPC に限定している理由

PostgreSQL の RLS は**行**しか絞れません。
「作業チェックの列だけ更新してよい」という制約は RLS では書けないので、
`SECURITY DEFINER` 関数を窓口にしています。

```sql
app.set_work_progress(item_id, step, done)   -- 作業チェック
app.update_delivery_fields(item_id, ...)     -- コンディション・付属品・追跡番号
app.find_by_sku(sku)                         -- SKU 検索
```

いずれも `app.assert_can_work_on()` で担当者本人か確認します。
`items` への直接 UPDATE は RLS で 0 行になるため、
アプリ側を書き換えられても仕入金額を触ることはできません。

この挙動は `supabase/tests/smoke.sql` で検証しています。

## 監査ログ

`app.items` への INSERT / UPDATE / DELETE はすべて `app.audit_log` に
変更前後の JSON ごと残ります。古物台帳は訂正の履歴が追えることが求められるため、
**行の物理削除は避け、`status = '廃棄'` を使ってください**（削除できるのは管理者のみ）。
